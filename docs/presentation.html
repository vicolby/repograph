Локальный MCP-сервер + Neo4j

repograph

Граф связей между репозиториями: какие сервисы что вызывают,
какие terraform-модули используют.

Агент, работая в одном репозитории, за секунды понимает, с чем тот связан.

← → или клики для навигации · 10 слайдов

Проблема

Знания о связях живут в головах

  • Какой сервис дергает этот API? Кто еще пользуется этим terraform-модулем?
  • Ответы — в памяти команды, в чатах, в устаревших wiki.
  • Новый человек (или агент) в репозитории этого контекста не имеет.

repograph фиксирует связи как данные: репозиторий → связь → репозиторий, с доказательствами (evidence).

Архитектура

Как это устроено

OpenCode / Claude Code ⇄ stdio repograph MCP
Node 20+, TS strict ⇄ Bolt Neo4j 5
docker-compose
  • Один процесс на stdio — агент спавнит его как дочерний, секретов и сети нет.
  • Neo4j Community из docker-compose.yml: Bolt localhost:7687, UI localhost:7474.
  • Данные персистятся в Docker volume neo4j-data — переживают рестарты.
Возможности · 4 инструмента

Весь API — четыре тулзы

add_repo

Создать/обновить узел репозитория (upsert по нормализованному пути).

repo, type?, description?

add_relation

Связать два репозитория. Повтор того же триплета дописывает evidence.

from, to, type, evidence[], created_by?

get_related_repos

Соседи узла в обе стороны. Глубина 1–10, фильтр по типу связи.

repo, depth?, type?

search_repos

Нечеткий поиск по подстроке (путь + описание, без учета регистра).

query, limit? (default 20, max 100)
Умная нормализация

Принимает то, что под рукой

  • SSH: git@gitlab.com:shop/billing-api.git
  • HTTPS: https://gitlab.com/shop/billing-api
  • Готовый путь: shop/billing-api

Всё приводится к одному ключу shop/billing-api (суффикс .git отрезается без учета регистра), дубли невозможны.

Пример · шаг 1–2

Регистрируем репозитории и связь

  • add_repo — добавляем сервис биллинга
  • add_repo — добавляем terraform-модуль сети
  • add_relation — фиксируем: сервис использует модуль, с доказательством
add_repo({ repo: "git@gitlab.com:shop/billing-api.git", type: "service" })
add_repo({ repo: "shop/platform/network", type: "terraform-module" })
add_relation({
  from: "shop/billing-api", to: "shop/platform/network",
  type: "uses_infra", evidence: ["billing-api/main.tf:12: module \"network\""]
})
Пример · шаг 3–4

Спрашиваем граф

  • Месяц спустя агент в репозитории биллинга: «от чего я завишу?»
  • Точного идентификатора модуля никто не помнит — ищет по подстроке
get_related_repos({ repo: "shop/billing-api" })
→ [{ path: "shop/platform/network", type: "terraform-module" }]

search_repos({ query: "bill" })
→ [{ path: "shop/billing-api", type: "service" }]
Подключение

Оба агента — один сервер

OpenCode

opencode.json в корне проекта, сервер repograph типа local. Проверка: opencode mcp list → connected.

Claude Code

.mcp.json в корне (project scope). Один аппрув при первом запуске, дальше /mcp → connected.

Оба спавнят node dist/src/index.js против одного и того же Neo4j. Других тулов (Codex, Gemini…) нет — осознанно вне скоупа.

Старт за минуту

Одна команда для нового человека

git clone <repo> && cd repograph && ./scripts/setup.sh
  • Проверяет Node ≥ 20 и Docker, ставит зависимости (npm ci).
  • Создает .env при первом запуске, поднимает Neo4j, ждет healthy.
  • Собирает dist/ и смоук-тестит stdio-спавн — все 4 тулзы.

Повторный запуск безопасен: существующий .env не перезаписывается.

Качество

Проверено по-настоящему

  • 36 тестов, все зеленые — против реального Neo4j в disposable-контейнерах (testcontainers), без моков драйвера.
  • Строгий TypeScript, валидация входов через zod с понятными ошибками.
  • Живые проверки: оба клиента показывают connected, все 4 инструмента вызваны end-to-end против локального Neo4j.
